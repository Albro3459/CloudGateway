## Findings

### [P1] Backfill ignores a valid Counters/accountSlots.nextSlot when choosing new slot values, reissuing a slot vacated by a hard-deleted account
- **Where:** `releases/access-control-lists/backfill_account_slots.py:180` (`base = max(all_valid_slots) if all_valid_slots else 0`) through `:189` (`assignments[uid] = candidate`), contrasted with `Backend/API/src/repository.py:343-399` (`next_account_slot`).
- **What:** `next_account_slot()` (the runtime allocator) trusts a *valid* stored `nextSlot` as the candidate baseline directly (`candidate = valid_stored`, `repository.py:373`) and only re-derives from the live scan of assigned slots when the counter is absent/malformed (`repository.py:379-396`, the documented "recovery path"). `compute_plan()` in the backfill does the opposite unconditionally: `base` for new-slot candidates is *always* `max(all_valid_slots)` from the current live `Users` scan (`backfill_account_slots.py:180`), regardless of whether `raw_next_slot`/`counter_before` is valid. `counter_before` is only consulted afterward, to make sure the *counter document* itself is never written backward (`:217`) — it never raises the floor that new slot *candidates* are drawn from.
- **Failure:** Account A is provisioned normally; the counter reaches, say, 6 after A gets slot 5 (`nextSlot` now valid at 6). A is later hard-deleted, so its `Users/{uid}` document (and its `accountSlot: 5`) is gone; no other live account currently holds a slot above 3. An operator now runs this backfill for legacy accounts B and C that never triggered the lazy fallback. `all_valid_slots` from the live scan tops out at 3, so `base = 3`, and B/C get newly assigned slots 4 and 5 — reissuing A's old slot 5, even though `Counters/accountSlots.nextSlot` was a perfectly valid 6 the whole time and the runtime allocator would never have handed out 5 again. `counter_after` computation (`max(highest_after + 1, counter_before)` = `max(6, 6)`) then leaves the counter unchanged at 6, so nothing downstream flags an inconsistency — the reused slot value silently ships. This is the same "hard-deleted account's slot gets reissued" hazard ACL-B flagged (P2) for the runtime's counter-recovery path, except here it fires on the migration's *primary* path any time a valid counter sits above the current live max, not only when the counter is missing/malformed — i.e. it is strictly more reachable than the runtime finding it mirrors, and it is exactly the reuse scenario the README itself calls out as unsafe ("Slots are never reused, by design ... a hand edit that clears or lowers a slot risks a later allocation reusing it" — the live-scan-only `base` computation causes the same effect without any hand edit).
- **Fix:** When `counter_before is not None` (a valid stored counter), the candidate floor for new assignments must be `max(base, counter_before - 1)` (or equivalently start `missing_uids` numbering from `max(base, counter_before)`), matching `next_account_slot`'s trust of a valid stored counter as the baseline. Only fall back to the pure live-scan `base` when the counter is missing/malformed, mirroring the runtime's recovery-path condition exactly.

### [P2] Test suite has no case with a valid counter above the live max plus pending new assignments — the one case that would catch the P1 slot-reuse bug
- **Where:** `releases/access-control-lists/test_backfill_account_slots.py:191-200` (`test_valid_counter_at_or_below_max_is_advanced_never_reused`).
- **What:** Despite its name implying "never reused" coverage, this test only exercises `stale_counter in (1, 2)` where `provisioned = {"uid-a", "uid-b"}` and both uids are *already* assigned slots 1 and 2 — i.e. `missing_uids` is always empty, so `base` (derived from live slots) and `counter_before` never diverge and no new `candidate` is ever computed while a valid counter sits strictly above the live max. No test in `ComputePlanTests` combines a valid `raw_next_slot` greater than `max(all_valid_slots)` with a non-empty set of missing/unassigned uids.
- **Failure:** This is exactly the gap that let the P1 finding above (`compute_plan` assigning new slots from `base = max(all_valid_slots)` instead of respecting a higher valid `counter_before`) ship undetected — a test asserting, e.g., `compute_plan({"uid-a","uid-b"}, {"uid-a": 1}, 10)` with `uid-b` missing should assert `plan.assignments["uid-b"] > 9` (respecting the counter) but the current code would assign `2` (respecting only the live max), and no test catches it.
- **Fix:** Add a `ComputePlanTests` case with a valid counter above the live max *and* at least one uid needing a new assignment, asserting the new slot is `>= counter_before`, not just `> base`.

### [P2] No test coverage for the 400-write transaction guard
- **Where:** `releases/access-control-lists/backfill_account_slots.py:552-556` (`_apply_within_transaction`'s `write_count > MAX_TRANSACTION_WRITES` check) and `:670-679` (`main()`'s identical pre-check); `releases/access-control-lists/test_backfill_account_slots.py` has no test referencing `MAX_TRANSACTION_WRITES` at all.
- **What:** The README calls this guard out as the load-bearing safety mechanism that keeps a single-transaction migration from ever running "halfway" ("The 400-write guard" section: "This script ... refuses to run if the plan would need more than 400 writes"). Neither the CLI-level pre-check in `main()` nor the in-transaction check in `_apply_within_transaction` has a test exercising the boundary (400 writes allowed, 401 blocked) or the refusal path (exit code, zero writes, `MigrationAbortedError` inside the transaction).
- **Failure:** A future edit to either check (e.g. changing `>` to `>=`, or miscounting the `+1` for the counter write) would silently change the guard's boundary with no test to catch it, and the only way to discover the regression would be to actually approach 400 pending legacy accounts on a real fleet.
- **Fix:** Add a `ComputePlanTests`/`ApplyTransactionTests` case with a plan sized to exactly `MAX_TRANSACTION_WRITES` (allowed) and one at `MAX_TRANSACTION_WRITES + 1` (refused with zero writes), covering both the `main()` pre-check and `_apply_within_transaction`'s in-transaction check.
