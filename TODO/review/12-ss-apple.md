### [P1] `Int(Double)` conversion trap in the mesh Firestore mapper crashes on a boundary value
- **Where:** `Frontend/Apple/CloudGatewayKit/Sources/CloudGatewayAppCore/CloudGatewayFirestoreMeshMapper.swift:128-132` (`integer(_:)`), reached from `meshPort` (line 119-124, used for `wireguardPort` and mesh peer `endpointPort`) and `displayOrder` (line 96-107, used for `Regions/*.displayOrder`).
- **What:** `integer(_:)` guards a `Double` -> `Int` conversion with a hand-rolled range check (`value >= Double(Int.min), value <= Double(Int.max)`) instead of `Int(exactly:)`. `Double(Int.max)` rounds up to exactly `2^63` (since `Int.max` = `2^63 - 1` is not representable as a `Double`), so a Firestore field whose numeric value is exactly `2^63` (`0x1p63` / `9223372036854775808`) passes the guard (`2^63 <= 2^63`) and then `Int(value)` traps at runtime because `2^63` is one past `Int.max`. This is the identical bug class already found and fixed in `CloudGatewayFirestorePolicyMapper.swift`'s `rowCount` helper (commit `24a0e80`, "Fix policy rowCount Int conversion trap"), but that fix (`Int(exactly:)`) was not applied here.
- **Failure:** A `Regions/{id}` document with `displayOrder: 9223372036854775808` (or a `wireguardPort`/mesh peer `endpointPort` field set to the same value, whether via a compromised/misconfigured backend write, a Firestore console edit, or any future writer that doesn't validate) causes any client that maps that document — Server Health, mesh status derivation, region listing — to crash with a Swift integer-conversion trap the next time it reads that collection. Not covered by existing tests: `CloudGatewayMeshStatusTests.swift` tests `1e30` and `Double.infinity` for `displayOrder`/`wireguardPort` (lines ~569-578), both of which are safely rejected by the existing guard since they exceed `Double(Int.max)`; none test the exact `2^63` boundary that trips the bug, unlike the sibling `CloudGatewayPolicyStatusTests.swift` which now explicitly covers `0x1p63` and `-0x1p65` after the policy-mapper fix.
- **Fix:** Replace `integer(_:)`'s body with `Int(exactly: value)` (matching the policy mapper's fix), or inline `Int(exactly: number.doubleValue)` at each call site the way `CloudGatewayFirestorePolicyMapper.rowCount` now does. Add a regression test asserting `meshRegion(...).displayOrder`/`wireguardPort` is `nil`-safe (falls back to default / nil) for `0x1p63` and accepts `-0x1p63` as `Int.min`.

### [P1] `CloudGatewayServerHealthViewModel` is a session-long singleton with no sign-out/account-swap reset, so a shared device can leak one admin's sync log (emails, client names, public keys, tunnel IPs) to the next admin who signs in
- **Where:** `Frontend/Apple/CloudGatewayKit/Sources/CloudGatewayAppCore/CloudGatewayServerHealthViewModel.swift` — the class has no reset/clear method at all (contrast with `CloudGatewayViewModel.clearRemoteState()` at `CloudGatewayViewModel.swift:1288-1310`, which explicitly nils out the old `syncResult` — see the removed `syncResult = nil` in the diff at `CloudGatewayViewModel.swift:1298` (old) — every time the identity changes); `syncResults` (`CloudGatewayServerHealthViewModel.swift:21`) and `dataAvailable` (`:20`) are set only by `apply()` (`:210-227`, called from `load()`/`syncAll()`) and `syncAll()` (`:167`), never cleared. `Frontend/Apple/iOS/CloudGateway/CloudGatewayIOSCompositionRoot.swift:64` constructs exactly one `CloudGatewayServerHealthViewModel` per app process in `CloudGatewayIOSComposition`, independent of and outliving any individual sign-in session. `Frontend/Apple/iOS/CloudGateway/ContentView.swift:92-112` reactively dismisses the `fullScreenCover` (`ContentView.swift:167-171`) when `appMode` leaves `.signedIn` or `role` stops being admin, but never calls anything on `serverHealthViewModel` to clear its published state.
- **What:** `apply(regions:meshDocs:policyResult:)` (`CloudGatewayServerHealthViewModel.swift:210-227`) overwrites `regions`/`meshDocs`/`policyRows`/`linkRows`/`warnings` on every `load()`, but `syncResults` — set once by `syncAll()` (`:167`) — is never reset by `load()`, by sign-out, or by an admin identity change. `dataAvailable` (`:20`, flipped `true` at `:226`) is likewise never reset, so `ServerHealthView`'s `unavailablePanel` gate (`ServerHealthView.swift:70-71`, `if !viewModel.dataAvailable`) does not fire for a re-opened page even though the data on screen is from a different signed-in user.
- **Failure:** Two admins share a device (a NOC iPad, a shared test device, or one admin handing a signed-in phone to another during a shift change — realistic for the small, trusted `UserRoles/*.roleId == "admin"` operator role this page is gated on, per `Backend/Firebase/firestore.rules:19`). Admin A signs in, opens Server Health, taps "Sync All Regions", and sees the fan-out result — `RegionSyncResultCard`'s `response.log`, which by the file's own header comment (`ServerHealthView.swift`, "SECURITY: `response.log` carries user emails, client names, client IDs, public keys, and tunnel IPs") contains real end-user PII and WireGuard public keys for the whole fleet. Admin A signs out. Admin B signs in with a different account and still holding the admin role. Because `serverHealthViewModel` is the same long-lived singleton object (`CloudGatewayIOSCompositionRoot.swift:64`), and `ContentView.swift:92-112` only toggles the sheet's *presentation*, not the underlying view model's state, Admin B opening Server Health (`ContentView.swift:169-171`) renders the fully-populated dashboard immediately — including Admin A's stale "Client peer sync" cards with their embedded log, PII, and keys — before Admin B has run any sync themselves. `syncResults` stays exactly as Admin A left it indefinitely, since nothing in the reload path clears it; `regions`/`meshDocs`/`policyRows` are eventually overwritten by the `.task { await viewModel.load() }` on `ServerHealthView.swift:29-31`, but only after that async call resolves, so even those render Admin A's stale values for one frame first (`dataAvailable` was never reset, so `unavailablePanel`'s loading state doesn't gate the stale render). This is the same class of cross-session leak `CloudGatewayViewModel.clearRemoteState()` was written to prevent for the now-removed single-region `syncResult` (old `CloudGatewayViewModel.swift:1298`, deleted in this diff) — that protection was not carried over when the sync-result surface moved to `CloudGatewayServerHealthViewModel`.
- **Fix:** Give `CloudGatewayServerHealthViewModel` a `reset()`/`clearState()` that nils `syncResults`, clears `regions`/`meshDocs`/`policyRows`/`linkRows`/`warnings`, and flips `dataAvailable`/`isLoading`/`isSyncing` back to their initial values, and call it from `CloudGatewayViewModel`'s existing identity-change path (`handleAuthState`'s `clearRemoteState()` call site, `CloudGatewayViewModel.swift:1062-1065`) or from `ContentView`'s `onChange(of: viewModel.appMode)`/`onChange(of: viewModel.role)` handlers (`ContentView.swift:92-112`) alongside the existing `isShowingServerHealth = false`. Add a regression test mirroring `CloudGatewayViewModelTests.testSyncCompletionCannotPublishPreviousUsersAuditLog`'s intent (removed in this diff, not replaced for the new view model) asserting `syncResults`/`dataAvailable` are cleared across a `service.currentUser` identity change.
