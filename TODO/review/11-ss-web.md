## Findings

### [P2] Cross-tab auth race can strand a completed sign-in on the Login page
- **Where:** `Frontend/Web/src/pages/Login.tsx:205-206` (also 231-232, 259-260) and the observer at `:299-315`
- **What:** `authUid` is updated on every `onAuthStateChanged` fire (line ~304), including while a manual sign-in attempt is in flight (`manualSignIn === true`) and that attempt's own `manualUserUid` is still `null` (comment at line ~29 explains this is deliberate: the invalidation check at 311-312 is skipped whenever `manualUserUid` is falsy, so `authUid` is allowed to silently track an unrelated concurrent auth-state change). When the manual attempt's own sign-in promise later resolves, it unconditionally compares its own uid against whatever `authUid` happens to hold at that moment (`if (attemptStateRef.current.authUid && attemptStateRef.current.authUid !== result.user.uid) manualInvalidated = true`). If `authUid` was set by a stale/unrelated auth event that arrived and was already superseded, this marks a *successful, current* sign-in as invalidated.
- **Failure:** Open the login page in two tabs of the same browser (Firebase Auth persistence syncs `onAuthStateChanged` across same-origin tabs). In tab A, click "Sign in with Google" and leave the popup open. Before it resolves, complete a sign-in with a different account in tab B. Tab A's auth observer fires with tab B's uid while `manualSignIn` is true and `manualUserUid` is still null, so it silently sets `authUid = uidB` without invalidating anything (the observer's own `fetchUserData` also no-ops here since `manualSignIn` is true, so this event triggers no navigation either). When tab A's own Google popup then resolves with `uidA`, the code sets `manualUserUid = uidA` and compares it against the now-stale `authUid (uidB)`, incorrectly setting `manualInvalidated = true`. `navigateProvisionedUser`'s `isCurrent()` check then aborts silently (no error shown), `signingIn` flips back to `false` in the `finally` block, and the login form re-appears as if nothing happened — even though tab A's Firebase `currentUser` is now legitimately `uidA`. Because Firebase's internal listener for `uidA` fires *before* control returns to the `await signInWithGoogle()` continuation (state update + listener notification happen inside the SDK prior to promise resolution), that event was already consumed and ignored while `manualSignIn` was still `true`, so no further `onAuthStateChanged` event arrives to retry the navigation. The user is stuck on the login page despite being signed in, and must manually reload to reach `/home`.
- **Fix:** Scope `manualUserUid`/`manualInvalidated` per attempt (e.g. capture them in a small per-attempt object returned by `beginManualAttempt` instead of shared mutable fields on `attemptStateRef`), or re-check `auth.currentUser` after the popup promise resolves instead of trusting a possibly-stale `authUid` snapshot, so a genuinely-current sign-in can't be invalidated by an unrelated event that arrived and was already dismissed earlier in the same window.

### [P2] "Sync All Regions" is not gated on an in-flight mesh-membership toggle
- **Where:** `Frontend/Web/src/pages/ServerHealth.tsx:520-534` (button `disabled` prop), vs. the toggle write path at `:302-347` (`handleToggleMesh`) and `togglingRegionIds` state (`:152`, `:549`, `:573`)
- **What:** The "Sync All Regions" button's `disabled` expression is `syncing || !enabledRegions.length` (line 526) — it does not check `togglingRegionIds.size`. `handleToggleMesh` updates the UI optimistically (`setRegions` at line 318) *before* `setRegionMeshEnabled` (the Firestore write) resolves, and `enabledRegions`/`confirmSync` read directly from that optimistic `regions` state (line 357: `enabledRegions.map(region => region.regionId)`), not from confirmed-persisted state.
- **Failure:** An admin checks the mesh-membership box for a newly-enabled region, then immediately clicks "Sync All Regions" (a natural admin action, not an edge case) before the checkbox's own `setRegionMeshEnabled` Firestore write has acknowledged. The confirm modal is not gated on `togglingRegionIds` either (`SyncRegionsConfirmModal` just receives `enabledRegions`), so the fan-out can start and reach the backend before the write commits. If the regional host reads `Regions/{id}.meshEnabled` from Firestore to decide mesh peer inclusion and that read lands before the toggle's write is durable, that region is silently skipped from this sync pass — the admin sees "Synced" with no error, while the mesh link for that region is still not applied, only surfaced later as "Pending" on the link-status card that they'd have to notice and re-run Sync for.
- **Fix:** Disable the "Sync All Regions" button (and/or the confirm action) while `togglingRegionIds.size > 0`, or await all in-flight `handleToggleMesh` writes before calling `runSync`, so a sync always fans out from state that is actually durable in Firestore.

- `src/helpers/meshValidation.ts` — verified CIDR/hostname parsing at HEAD. No 32-bit bitwise arithmetic is used anywhere (network math is octet/word comparison, not `<<`/`|` shifts), so the classic `>= 128.0.0.0` overflow class of bug does not apply. IPv4 parsing rejects leading zeros and out-of-range octets; IPv6 parsing correctly rejects multiple `::`, requires exactly 8 words when uncompressed, and `formatIPv6Canonical` implements RFC 5952 canonical compression (longest run wins, leftmost tiebreak, no compression of single zero words) and is used to force canonical-only input. Mesh v4/v6 network validators are deliberately scoped to a fixed `10.0.x.0/24` / `fd42:42:42:x::/64` range (not general CIDR), and `networksOverlap` compares exactly the octet/word range that distinguishes those fixed-width subnets, which is correct given the scoping. No bug found.
