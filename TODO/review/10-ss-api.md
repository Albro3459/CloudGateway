### [P2] Hung DNS resolution during mesh drift-check leaks worker threads in the long-lived API process
- **Where:** `Backend/API/src/wireguard.py:723-746` (`_resolve_endpoint_addresses`), called from `mesh_peer_drifted` (`wireguard.py:973-993`) via `LocalWireGuardManager._mesh_peer_drifted` (`wireguard.py:502-503`) during `sync_peers` (`wireguard.py:462`).
- **What:** Every mesh-peer drift check spins up a fresh `ThreadPoolExecutor(max_workers=1)` and submits `socket.getaddrinfo(host, None, type=socket.SOCK_DGRAM)`, which has no built-in timeout. `future.result(timeout=ENDPOINT_RESOLVE_TIMEOUT_SECONDS)` only bounds how long the *caller* waits; on timeout the code does `executor.shutdown(wait=False)` and returns `()`, explicitly leaving the submitted `getaddrinfo` call running in its own thread ("abandoned (never joined)" per the comment at `wireguard.py:724-727`). If a mesh peer's DNS name resolves to a resolver that hangs indefinitely (e.g. a firewall silently drops the DNS query with no ICMP/RST, as opposed to a clean NXDOMAIN/refused/timeout), that worker thread never exits.
- **Failure:** `sync_peers` is reachable from the long-running FastAPI process via `POST /admin/sync` (`routes.py:664`, `outcome = run_sync(...)`), not just the one-shot `cloudgateway-sync-peers` systemd unit. If one enabled mesh region's `wireguard_endpoint_hostname` points at a host whose DNS silently hangs, every "Sync All" admin call (manual retries, or any automated poller hitting the endpoint) leaks one more OS thread in the API server's process for as long as that condition persists. Because the leaked thread is a plain `ThreadPoolExecutor` worker with `wait=False`, nothing ever joins or caps it - repeated calls accumulate threads without bound in the same long-lived process, eventually risking `RuntimeError: can't start new thread` / resource exhaustion for the whole regional API, not just the mesh feature.
- **Fix:** Reuse a single bounded, module/instance-level executor (or a small fixed-size pool) for endpoint resolution instead of creating one per call, and/or track and cap in-flight resolution attempts per host so a permanently wedged resolver can't cause unbounded thread growth in a process that outlives a single sync pass.

### [P2] Route-reconciliation failure bypasses the partial-progress log and can silently discard an earlier mesh-peer apply error
- **Where:** `Backend/API/src/wireguard.py:474-500` (`sync_peers`), `wireguard.py:529-605` (`_reconcile_mesh_routes`/`_reconcile_routes_for_family`).
- **What:** When a mesh peer fails to apply (`_apply_mesh_peer_command` raising inside the `for public_key, peer in mesh_by_key.items()` loop at `wireguard.py:429-448`), the exception is caught, logged per-peer (`Event.MESH_PEER_APPLY_FAILED`), and stashed in `apply_error` so the loop can keep going and isolate the failure. But `route_changes = self._reconcile_mesh_routes(routed_mesh, known_mesh_networks)` at `wireguard.py:474` is called unconditionally afterward with **no try/except**. If an `ip route replace`/`ip route del` call inside it fails (`_run` raises `WireGuardApplyFailedError`, exactly as tested in `test_route_add_failure_after_peer_mutation_repairs_on_next_sync` and the `test_route_removal_failure_preserves_partial_state_until_next_rollback_sync` parametrized test in `Backend/API/tests/test_wireguard.py:845-887`), that exception propagates immediately and unwinds out of `sync_peers` — it never reaches the `if apply_error is not None: log_event(..., Event.PEER_SYNC_PARTIAL, ...); raise apply_error` block at `wireguard.py:481-498`.
- **Failure:** If a mesh-peer apply failure occurs (e.g. one region's DNS is broken, setting `apply_error`) in the *same* pass where a subsequent `ip route` call also fails (e.g. a transient netlink/kernel error, or `COMMAND_TIMEOUT_SECONDS` is hit on the route call), the route-reconciliation exception is what actually propagates to the caller — the original `apply_error` (and its `Event.MESH_PEER_APPLY_FAILED` context) is silently dropped, and the `Event.PEER_SYNC_PARTIAL` summary log (added/updated/removed/mesh_applied/routes_added counters) that exists specifically so an operator can see what already landed before a failed pass is never emitted for this path. `main()` in `sync.py` then just logs the route-failure message via `PEER_SYNC_FAILED` with no indication a peer also failed to apply in the same pass. Both `test_route_add_failure_after_peer_mutation_repairs_on_next_sync` and `test_route_removal_failure_preserves_partial_state_until_next_rollback_sync` exercise a route failure in isolation and confirm the pass still converges on the next sync (so this is not tunnel-breaking), but neither test — nor any other in `test_wireguard.py` — combines a mesh-peer apply failure with a route-reconciliation failure in the same pass, so this gap in error-visibility is untested.
- **Fix:** Wrap `_reconcile_mesh_routes` the same way the peer-apply loop is wrapped: catch `WireGuardApplyFailedError` there, fold it into `apply_error` (only if one isn't already set, preserving the first/root cause), and always emit the `Event.PEER_SYNC_PARTIAL` summary log with a best-effort `route_changes` snapshot before re-raising.
